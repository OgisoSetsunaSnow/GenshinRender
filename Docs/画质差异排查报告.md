## 2. 唯一的架构差异：后处理实现

参考工程的自定义后处理（Bloom + ColorGrading）是 URP 14 写法：

```
Execute(ScriptableRenderContext, ref RenderingData)
  → CommandBuffer + CommandBufferPool
  → RTHandle + RenderingUtils.ReAllocateIfNeeded 手动管理
  → Blitter.BlitCameraTexture(cmd, src, dst, material, pass)
  → renderingData.cameraData.renderer.cameraColorTargetHandle
```

URP 17 里 `Execute(ref RenderingData)` 已废弃，我按官方 RenderGraph API 重写：

```
RecordRenderGraph(RenderGraph, ContextContainer)
  → renderGraph.CreateTexture(desc) 自动管理生命周期
  → renderGraph.AddRasterRenderPass<PassData>() + builder.SetRenderAttachment()
  → ctx.cmd.DrawProcedural(matrix, material, passIndex, Triangles, 3, 1, mpb)
  → resourceData.activeColorTexture 读 / resourceData.cameraColor 写回
```

**着色器代码和参数都照搬，但宿主代码是重写的。**

Bloom 链结构两边一致：

```
Prefilter(降到 0.5 倍) → BlurH1x → BlurV1x
  → 3 次 {BlurH2x(降采样) → BlurV1x}
  → Upsample(4 级按 weights 加权)
  → ColorGrading(加 Bloom → ×Exposure → Tonemap → Contrast → Saturation)
```

## 6. 测量数据

测量方法：截取角色躯干固定区域，计算平均亮度(mean)、亮度标准差(std，代表对比度)、
拉普拉斯方差(lapVar，代表锐度)。**区域完全避开背景**。

### 胸腹区域

| 状态 | mean | std | lapVar |
|---|---|---|---|
| 目标：关全部后处理 | 137.3 | 52.40 | 3782 |
| 目标：只开 tonemap + exposure 1.05 | 138.7 | 56.10 | 4648 |
| 目标：再加 Bloom (1.5 / 0.7) | 149.6 | **50.26** | **3247** |
| **参考：全开** | **162.5** | **65.04** | **5627** |
| 目标：调参后 (bloom .55/.86, exp 1.16) | 144.6 | 57.90 | 4921 |
| 目标：描边 1.0 + contrast 12 | 146.3 | 60.35 | 5097 |

### 裙摆区域

| 状态 | mean | std | lapVar |
|---|---|---|---|
| 目标：关全部后处理 | 180.6 | 27.55 | 1430 |
| 目标：只开 tonemap | 182.6 | 24.53 | 1411 |
| 目标：再加 Bloom (1.5 / 0.7) | 188.9 | **20.50** | **781** |
| **参考：全开** | **217.5** | **33.06** | **1778** |
| 目标：调参后 | 192.8 | 24.99 | 1379 |

### 由数据得出的结论

1. **tonemap 不压对比度**：52.40 → 56.10（+7%），锐度 3782 → 4648（+23%）。
2. **Bloom 是"糊"的直接来源**：对比度 56.10 → 50.26（-10%），锐度 4648 → 3247（-30%）；
   裙摆更严重，锐度 1411 → 781（**-45%**）。
3. **但即使关掉 Bloom**，目标工程对比度 56.10 / 24.53 仍低于参考最终输出 65.04 / 33.06。
   也就是说：**亮度与对比度的基线差异存在于后处理之前**。

## 8. 剩余可疑点（未验证）

1. **URP 14 → 17 的光照计算差异**
   `GetMainLight()`、阴影衰减、`TransformWorldToViewNormal` 等实现在两个大版本间有改动，
   可能导致同样的 `intensity 1` 下，shader 拿到的光照量不同。

2. **我们的 RenderGraph Bloom 能量比参考强**
   在完全相同的 `intensity 1.5 / threshold 0.7 / weights` 下，
   我们的 Bloom 造成的对比度损失（-10% / -16%）明显大于参考（参考最终 std 反而更高）。
   怀疑 `_BlurRadius`、`_BlitTexture_TexelSize`、或 Upsample 的能量归一化与参考不等价。

3. **截图管线的 HDR→SDR 转换差异**
   两边都是通过 MCP 工具的 `screenshot` 抓图，Unity 6 与 2022 的底层可能不同。
   尚未用系统级截图（Game View 直接抓屏）交叉验证。

4. **缺少 Ground 平面**
   参考有地面，可能影响环境反射探针 / 间接光，进而影响角色亮度。

5. **背景 Quad 尺寸不同导致构图差异**
   参考 17.78×10 @ z=-1（相机距离 2.4），目标 5.6×3.2 @ z=1.6（距离 3.0）。
   角色在画面中的占比不同，会让像素级指标对比不完全公平。

## 16. 剩余可疑点（按价值排序）

### P0-1 Camera Stacking 结构不同
参考：`BaseCamera(Base) + MainCamera(Overlay) + BackCamera`，`cameraStack` 挂在 BaseCamera 上。
目标：单相机。
URP 的相机栈会把后处理施加在**栈的最终输出**上，而单相机施加在单个相机的颜色目标上。
两者在 RT 往返、色彩空间转换、resolve 行为上可能不同。
**未验证**。

### P0-2 URP HLSL 依赖的实际编译结果不同
`URPGenshinToon.shader` 文件相同（GUID 419678），但它 include 的是 URP 包内的
`Core.hlsl` / `Lighting.hlsl` / `RealtimeLights.hlsl` / `Shadows.hlsl`。
URP 14.0.12 与 17.6.0 的这些文件实现有差异，`GetMainLight()`、阴影衰减、
`TransformWorldToViewNormal` 的实际行为可能不同。
**未验证**（需要对两个版本的 HLSL 做依赖树 + 哈希 + 关键函数 diff）。

### P1 Mesh 法线 / 切线
FBX 相同不代表导入结果相同。Unity 6 与 2022 的 Model Importer 默认值可能不同
（Normals、Tangents、Mesh Compression、Optimize Mesh、Weld Vertices）。
法线直接决定 Toon 阴影分界线、描边宽度、Rim。
**未验证**。

### P1 父材质 `Nahida_Base` 的完整审计
已 diff 10 个 .mat 的 YAML 参数，但未核查 Shader Keywords、Render Queue、
Override Tags、Shader Pass Enable、Material GI Flags、GPU Instancing。
另外目标工程比参考多了一个 **MaterialPropertyBlock**（自定义 `MaterialUpdater` 用来写 `_FaceDirection`），
MPB 会覆盖材质属性并破坏 SRP Batcher，需要确认它没有副作用。

### P2 分辨率与投影尺寸
参考 1166×632 / aspect 1.845，目标 1103×623 / aspect 1.770。
分辨率差 5.4%，lapVar 按分辨率平方缩放应差约 11%，**不足以解释 31~44%**，但仍然是噪声源。
建议统一 Game View 分辨率后重测。

### P2 缺少 Ground Plane
参考有地面。但角色 shader 若未采样 SH / Lightmap / Reflection Probe，
加地面不会自动提升亮度。需要先确认参考是否用了 Light Probe / Reflection Probe / APV。

## 17. 建议的下一步（严格按顺序，每次只改一个变量）

1. **统一 Game View 分辨率**到 1166×632（或同一值），两边重测实验 A → 消除分辨率噪声
2. **在目标工程临时搭 Base + Overlay 双相机**，其余不动，重测 → 验证 Camera Stacking 影响
3. **对 URP 14 / 17 的 HLSL 依赖做哈希与关键函数 diff** → 验证光照输入是否等价
4. **导出两边 Mesh 的 normals / tangents 逐顶点对比** → 验证法线是否一致
5. 以上都排除后，再做 Bloom 逐级能量对比

> 在此之前，所有"调参数让画面看起来更接近"的操作都只是掩盖问题，不应作为诊断依据。

# 第三轮：根因定位（最终结论）

## 18. 根因：URP 17 的 URP Asset 级默认 Volume Profile

**`PC_RPAsset.asset` 上挂着一个 `SampleSceneProfile`，内含 Tonemapping / Bloom / Vignette，全部 active。**

这是 URP 17（Unity 6）新增的机制：URP Asset 自身可以携带一个全局 Volume Profile，
它**独立于场景里的 Volume 组件**。因此：

- 禁用/删除场景中的 `Genshin Post Process Volume` **不会关掉它**
- 之前所有"关后处理"的对照实验，实际上一直在它之上进行
- 我们自定义的 Bloom 与它叠加，导致调参永远调不到预期

参考工程是 URP 14，没有这个字段，它的"关 Volume"是真正的关闭。
**这就是为什么两个工程资产完全一致、参数完全一致，画面却始终对不上。**

### 验证方法（单变量）

对同一工程、同一场景、同一帧，只改 `m_VolumeProfile` 一个字段：

```csharp
var so = new SerializedObject(urpAsset);
so.FindProperty("m_VolumeProfile").objectReferenceValue = null;
so.ApplyModifiedProperties();
```

### 验证结果（两边均关闭场景 Volume）

| 区域 | 指标 | 有 Profile | Profile 置空 | 参考 2022 |
|---|---|---|---|---|
| 胸腹 | mean | 141.1 | **153.1** | 150.5 |
| 胸腹 | std | 52.90 | **66.44** | 65.88 |
| 胸腹 | lapVar | 3520 | **5111** | 5635 |
| 裙摆 | mean | 180.3 | **205.9** | 205.6 |
| 裙摆 | std | 27.71 | **40.61** | 41.05 |
| 裙摆 | lapVar | 1326 | **2381** | 2562 |

置空后与参考的差距从 20~48% 收敛到 0.15~9%。

### 恢复后的最终对比（两边都开后处理，参数全部为参考值）

| 区域 | 指标 | 目标 | 参考 | 比例 |
|---|---|---|---|---|

**从 0.52~0.80 收敛到 0.94~1.01。**

## 22. 一句话总结（修订）

**根因不是版本、不是 shader、不是材质、不是 API，而是 URP 17 在 URP Asset 上默默挂着一个
默认 Volume Profile，让所有"关闭后处理"的对照实验都失效。**

排查过程中被推翻的错误结论：
1. ~~"基线差异在后处理之前就存在，是管线本身的问题"~~ → 错，是没关掉的后处理
2. ~~"需要把曝光补偿到 1.16、对比度加到 12 来追平"~~ → 错，补偿的是不应该存在的效应
3. ~~"描边要降到 1.0 才不糊"~~ → 错，糊的是 Bloom，描边一直是参考值 1.6

**教训：先确认"关闭"是真的关闭，再做对照实验。**
